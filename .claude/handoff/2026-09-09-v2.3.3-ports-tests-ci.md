# Handoff — 2026-09-09 (v2.2.0 through v2.3.3)

## TL;DR

Four releases with no handoff until now. Nothing user-facing changed in any
of them. What changed is that the code is now testable and CI actually
verifies it.

The headline number: **the test suite went from 1 test to 69, and that one
test had never executed.** The harness was broken in a way that reported
nothing.

## What happened, in the order it mattered

### The test suite had never run

`npm test` failed with `spawn …/Contents/MacOS/Electron ENOENT`.
`@vscode/test-electron@2.5.2` looks for an executable named `Electron`;
VS Code 1.134's macOS bundle names it `Code`. Upgrading to 3.1.0 fixed it.

With the harness working, the single pre-existing test turned out to assert
against an extension that never activated — no `activationEvents`, nothing
in a test run triggers lazy activation, and a contributed-but-inactive
command is not in the command registry.

So the starting position was not "one test". It was zero.

### Two ports, each replacing a place a defect had shipped

**`ActiveEditorSource`** (2.2.0). The staleness rules read
`vscode.window.activeTextEditor` from inside a predicate, so they could not
be driven from a test. `isStale` was the only staleness predicate with no
coverage, and two of the three defects fixed in 2.1.0 were staleness bugs.

**`CommandRunner`** (2.3.0). `editor.action.codeAction` applies nothing in
the test host — measured across `apply: "ifSingle"`, `"first"` and
`"never"`, plus `editor.action.refactor`, while `workspace.applyEdit` works
fine. The widget needs UI the host does not drive.

That mattered more than it sounds. Asserting "the document is unchanged"
**passes even with the staleness guard deleted**. Two such tests were
written, looked green, and were removed once a mutation run exposed them.
Committing them would have been worse than no tests: they would have read as
coverage of the one path that had already broken once.

### CI was green and proved almost nothing

The workflow ran `check`, `compile` and `package`. It never ran `lint` or
`test`. Sixty-nine tests only ever ran on one Mac.

Meanwhile every tag push since v2.2.0 failed, while the matching `main` push
passed. The `publish` job ran `vsce publish` against a `VSCE_PAT` secret that
does not exist — Azure DevOps answers `TF400813: the user
'aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa' is not authorized` for an absent
token. That secret was never coming: the Azure DevOps organisation a PAT
requires kept demanding a payment card, so this project moved to manual
upload months ago. The job was waiting on a credential the project had
already decided not to have.

The tag build now attaches the VSIX to the GitHub Release instead.

### Three things that passed locally and failed on Linux

Adding `test` to CI surfaced all three at once:

1. The suite drives a real VS Code, so Linux needs `xvfb-run -a`.
2. The TypeScript language server answers instantly on a warm Mac and not at
   all on a cold runner. A test that assumes readiness reads an empty
   prefetch as "nothing was dispatched, as expected" — passing for the wrong
   reason locally, failing honestly in CI.
3. Polling that server in a tight loop gets in-flight requests cancelled. The
   rejection escaped a `suiteSetup`, and **a throwing hook takes its whole
   suite with it**: the run reported 63 passing where `main` had 69.

The third is the one worth remembering. The single failure was the decoy;
**the five tests that never ran were the signal.** Compare totals, not
failure counts.

## Every new test was mutation-checked

A passing test is not evidence it can fail. Each suite was verified by
breaking the code it covers:

| Area | Mutations tried | All caught |
|---|---|---|
| `migrate-settings` | invert the `false` guard, drop the already-set check, skip clearing the deprecated key, write `true`, collapse the workspace scope | yes |
| `run-refactor` | delete the guard, move it before the prefetch, ignore availability, hardcode the kind, drop the chain fallback | yes |
| `go-to-declaration` | collapse `"stale"` into `"none"`, remove either staleness guard, invert the caret filter, drop the definition provider, disable dedupe, pin the goto behaviour | yes |

One mutation could not be built at all: replacing the availability check with
`if (false)` does not compile, because the narrowing that keeps `request`
defined goes with it. The compiler is the guard there.

Two others first reported "0 failing", which was wrong — orphaning an import
failed lint, `pretest` aborted, and the suite never ran. Reading that as "the
tests did not catch it" would have been backwards.

## Also verified, and left alone

- **`@types/vscode` was four versions ahead of the `engines` floor**
  (`^1.106.0` resolving to 1.110.0). Compiling against exactly 1.106.0 gives
  zero errors, so nothing newer is in use and the risk was latent. Pinned to
  1.106.0 anyway: the compiler now enforces the floor instead of trusting it.
- **TypeScript 7 is still blocked**, and the reason is precise rather than
  conservative. `@typescript-eslint/parser` calls `ts.createSourceFile`;
  TS 7.0.2's main entry exports two things and the compiler API lives behind
  `./unstable/*`. Its canary declares the same `<6.1.0` range. Recheck at 7.1.
- **Four npm advisories remain**, all needing a `@vscode/test-cli` major.
  They are devDependencies, the VSIX ships zero `node_modules` files, and the
  harness was just raised to 0.0.15 to fix the Electron naming problem. Not
  worth churning again for advisories that cannot reach the published
  artifact.
