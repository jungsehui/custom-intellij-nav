## The measurement method changed, and here is why

v1.1.0 through v1.3.0 measured VS Code defaults by `curl`-ing individual
source files and grepping them. That is unsound: a key can look free
merely because the file that binds it was never fetched.

It failed this time. `⌥F8` returned zero hits and was on its way to
shipping as "free". It is `editor.action.marker.next` — Go to Next Problem
(`gotoError.ts` L202). The bug surfaced only because a positive control
was run alongside it: `KeyCode.F5` returned 9 hits, `KeyCode.F9` returned
2, and `KeyCode.F8` returned 0, which is not a shape a real corpus
produces.

Measurement now runs against a full checkout:

```bash
git clone --filter=blob:none --sparse --depth=1 https://github.com/microsoft/vscode.git
cd vscode && git sparse-checkout set src/vs extensions   # 11,832 .ts files
```

Three instrument faults surfaced in the same pass, each returning a
plausible wrong answer instead of an error:

1. zsh expands an unquoted `--include=*.ts` before grep sees it.
2. `grep -c pattern file` on a **single** file omits the `file:` prefix,
   so an `awk -F: '{s+=$2}'` pipeline sums empty strings to zero. This
   reported 0 occurrences of `custom-intellij-nav` in the project's own
   transcript, where the real count is 5044.
3. A probe string typed into a command is written to the session
   transcript before a grep of that transcript runs, so a "must be zero"
   control can legitimately return 2. Do not mistake that for a fault.

Rule now in `.claude/conventions.md`: pair every zero-hit result with a
positive control **in the same command**.

## VSCodeVim: deferred to, not fought

The roadmap had listed 7 colliding keys as an open risk since v1.0.0.
The real count is 9 — `⌃J` and `⌃R` were missed.

VSCodeVim publishes a context key per key it claims
(`configuration.ts` L198: ``VSCodeContext.set(`vim.use${boundKey.key}`, useKey)``),
so each of ours now carries `!vim.use<C-x>`:

| Situation | Result |
|---|---|
| No VSCodeVim | Key undefined → our binding fires |
| VSCodeVim default | Vim wins |
| `"vim.handleKeys": {"<C-t>": false}` | Ours fires again |

Per key, not per category. The `<`/`>` is legal in a `when`: the scanner
regex allows it (`scanner.ts` L302) and VS Code unit-tests this exact
expression (`contextkey.test.ts` L392).

## Debugging keys now know whether you are debugging

All eight original Debugging bindings were gated on nothing but `isMac`,
so `F7` and `F8` fired at a dead debugger while permanently displacing
`wordHighlight.next` and `editor.action.marker.nextInFiles`. They now
carry `debugState == 'stopped'`, `inDebugMode && !focusedSessionIsAttach`,
or `debuggersAvailable` as appropriate. Outside a paused session the VS
Code defaults work again.

This is the same class of defect as the v1.3.0 `F6` fix: a key that
displaces a default while being unable to do anything.

## Displacements taken, and why they are cheap

| Key | Lost default | Already covered by |
|---|---|---|
| `⌃R` | Open Recent… | `⌘E` (IntelliJ's Recent Files) |
| `⌥F8` | Go to Next Problem | `F2` / `⇧F2` (IntelliJ's Next Error) |

Check for an existing second binding before judging a displacement
expensive. Both of these looked costly until the manifest was searched.

## Note on skills tooling

`SearchSkills` / `ListSkills` / `ListPlugins` query the **claude.ai**
account registry and cannot see locally installed plugin skills under
`~/.claude/plugins/`. An empty result there is not evidence a skill is
missing. Also, a session snapshots its skill listing at start, so a plugin
installed mid-session is unavailable until the session restarts — which is
why `/sehui-skills:fact-check-first` did not resolve between 2026-08-18
and 2026-08-20 in a session that began 2026-04-26.
